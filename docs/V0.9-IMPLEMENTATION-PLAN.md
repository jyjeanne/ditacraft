# DitaCraft v0.9.0 Implementation Plan — Refactoring, Templates & Publishing

---

## 1. Executive Summary

`ROADMAP.md` shows every milestone through v0.8.2 complete (1,770+ tests). The
next unclaimed work sits in **Milestone 6's deferred backlog** (Refactoring
Tools, Templates & Scaffolding, Productivity Features) and **Milestone 7 /
v0.9.0** (Publishing Enhancements). None of that work has design detail yet —
it's a flat checklist. This document turns the checklist into a prioritized,
technically-grounded plan: what each feature actually requires, which
existing services it can reuse, and in what order to build it.

**Method:** every candidate feature is scored on (a) how often an author
would hit the problem it solves, (b) how much it leverages infrastructure
DitaCraft already has (`KeySpaceService`, `referenceParser`, `workspaceScanner`,
`SubjectSchemeService`, the LSP rename/reference pipeline, existing WebView
panels), and (c) blast radius / risk. High value + high reuse + low risk sorts
to the top.

**Verification pass (this revision):** every "reuse" claim below was checked
against two independent, differently-implemented static-analysis tools rather
than taken on faith from file names and docstrings:

- **[graphify](https://github.com/rhanka/graphify)** (`docs/graph/graph.json`, already checked into this repo) — a tree-sitter-based call/import graph, queried per-symbol (`graphify explain <symbol>`) to confirm exactly which functions a proposed feature would actually touch.
- **[okf-rs](https://github.com/jyjeanne/okf-rs)** (a separate Rust CLI of the repo owner's; not a DitaCraft dependency) — built from source and run against a clean copy of `src/`, `server/src/`, and `mcp/src/` to independently regenerate an OKF knowledge bundle (1,208 concepts) and cross-check it against graphify's graph: `okf-rs validate` reports no structural issues, `okf-rs graph cycles` finds no call cycles, and spot-checking callers/callees for the functions this plan names (e.g. `handleRename`) via `okf-rs explore` agrees with graphify's edges. Where the two tools' independent implementations agreed, that's treated as corroboration; where a claim in the original draft turned out not to match either tool's evidence, it's corrected below with the exact line reference. One genuine defect surfaced this way is documented in §2.1 before the feature plan itself.
- **A second, deeper okf-rs pass** (this revision) went beyond corroborating file/function names and pulled *exact signatures, call counts, and blast radii* for the sections that had the least concrete detail — `DitaOtWrapper.publish`'s three real callers and its `PublishOptions` interface (§3.2, §4.5), `generateTopicContent`'s actual 2-argument signature (§4.1), and the one existing decoration-type and webview-message precedents in the client (§4.5, §5) — replacing "reuses X" one-liners with the specific insertion points (file:line) an implementer would actually start from. A caveat worth naming rather than hiding: without `--lsp`, okf-rs's tree-sitter-only call resolution occasionally links a bare `.get(...)`/`.method(...)` call to an unrelated same-named method project-wide (seen once, harmlessly, resolving `SubjectSchemeService`'s internal cache lookup to the client's `ConfigurationManager.get`) — real edges were cross-checked against the actual source before being written into this plan, not taken from the tool's output alone.

Every "Design" subsection below that changed as a result of this pass is
marked inline (search for "Correction" / "verified") rather than silently
rewritten, so it's clear which claims were checked and which were already
accurate.

### 2.1 New Finding — Client/Server `isPathWithinWorkspace` Divergence — ✅ FIXED

Not a roadmap item — a defect the verification pass surfaced by accident and
worth fixing regardless of which features get built next, since every
href-safety claim in this plan (§4.4 in particular) leans on this guard being
correct everywhere it's used.

**Status: fixed.** `src/utils/keySpaceResolver.ts` now has a
`normalizePathForComparison()` helper applying the same win32 case-fold
policy as the server's `normalizeFsPath()`, used by both sides of the
`isPathWithinWorkspace()` comparison; the "not equal to workspace root"
policy this method deliberately differs from the server's was left
untouched. Regression tests added in `src/test/suite/keySpaceResolver.test.ts`
("Workspace Boundary Path Normalization") — platform-conditional per this
codebase's existing convention (see `ditaOtWrapper.test.ts`/
`previewCommand.test.ts`), since there's no `sinon`-style platform-mocking
helper here the way the server's `textUtils.test.ts` has `withPlatform()`.
Verified via `tsc --noEmit` (client + server) and a full `npm run compile`;
the VS Code Electron integration suite itself (`npm test`) couldn't be run
in this sandbox — it needs to download a VS Code build from an update
server the environment's network policy doesn't reach — so the win32-only
assertions haven't executed against a real Windows host yet.

**What okf-rs's `graph isolated` output showed** that graphify's earlier,
narrower query didn't: there isn't one `isPathWithinWorkspace`, there are
**three**, and two of them are legitimate:

| Location | Kind | Verified behavior |
|---|---|---|
| `server/src/utils/textUtils.ts:128` | canonical, exported function | Delegates to `findContainingWorkspaceFolder()`, which explicitly uses `normalizeFsPath()` — lower-cased on `win32` — specifically *because* (per its own comment, `textUtils.ts:138-142`) a path reaching it via a `file://` URI round-trip (which `vscode-uri` lower-cases the drive letter of) must compare equal to the same path reaching it as a raw fs string. This is the fix the v0.8.2 changelog calls "Windows Path Case-Fold Normalization." |
| `server/src/services/keySpaceService.ts:1524` | private method, same name | Confirmed a thin wrapper: `return isPathWithinWorkspace(absolutePath, this.workspaceFolders);` (`keySpaceService.ts:1525`) — just binds `this.workspaceFolders` to the canonical function above. **Not a duplicate.** |
| `src/utils/keySpaceResolver.ts:160` | private method, same name, **client-side** | **An independent reimplementation**, necessarily — client code (`src/`) cannot import the server-only `textUtils.ts` under this project's client-server split. Its logic (`keySpaceResolver.ts:160-171`) does `path.normalize(absolutePath)` and a plain `.startsWith()` prefix check — **no case-folding on Windows**. |

**The gap:** the server-side guard was deliberately hardened against a
Windows drive-letter-case mismatch; this client-side namesake, which guards
the same class of operation (resolving a workspace-relative path before
trusting it) for the client's own key-space resolver, was not. A path that
differs from a configured workspace folder only in drive-letter case — e.g.
one obtained through a `file://` URI vs. one built from a raw `fs` path,
exactly the scenario the server-side comment names — would be wrongly
treated as *outside* the workspace by `src/utils/keySpaceResolver.ts` on
Windows, either denying a legitimate same-workspace reference or (worse,
depending on which branch relies on the check) failing open in a way the
server-side code was specifically changed to avoid.

**Recommended fix:** `src/utils/keySpaceResolver.ts` can't import the
server's `normalizeFsPath()`, but it can replicate the one-line policy
(`process.platform === 'win32' ? resolved.toLowerCase() : resolved`) — or,
better, this is a good argument for a tiny shared `src/utils/pathSafety.ts`
client-side utility mirroring the server's, with a code comment cross-
referencing `textUtils.ts` so the two don't drift apart again silently.
Either way, this needs its own regression test (a Windows-style mixed-case
path against a lower-case workspace folder) — the exact case the server-side
fix already covers in `textUtils.test.ts` per the v0.8.2 changelog, which
this client copy has no equivalent of today.

This is small (S effort) and independent of every other item in this
document — recommend doing it first, or in parallel with §3.1-3.3, since it
touches none of their files.

## 3. Phase 1 — Quick Wins (target: 2-3 weeks)

### 3.1 Rename Key Across All Usages — ✅ SHIPPED

**Gap today:** `server/src/features/rename.ts` only handles `id` attributes
(`findIdAtOffset` in `referenceParser.ts`). Renaming a `keys="product-name"`
value on a `<keydef>` requires manually editing every `keyref`/`conkeyref`
across the workspace — exactly the class of bug the existing ID-rename
feature was built to prevent.

**Design — corrected after tracing the actual reuse boundary** (the original
draft of this section overstated how much of `rename.ts` carries over
unchanged; verified against the live code, not just its docstrings):
- Add `findKeyAtOffset(text, offset)` to `server/src/utils/referenceParser.ts`, mirroring `findIdAtOffset` — but note `findIdAtOffset` currently hard-matches `attrName === 'id'` only (`referenceParser.ts:142`), so this is genuinely new matching logic, not a parameterization of the existing function. It must tokenize `keys="a b c"` on whitespace and resolve to the specific token under the cursor — reuse the exact tokenization already used for provenance tracking in `KeySpaceService.extractKeyDefinitions()` (`keySpaceService.ts:1053`, `keysValue.split(/\s+/)`), so the two don't drift on how a multi-key `keydef` is split.
- **`collectMatchingEdits`/`replaceIdInReference` are *not* directly reusable** — verified via `referenceParser.ts:201-205`: `referenceMatchesId()` explicitly `return`s `false` for `type === 'keyref'` ("keyref values are key names, not file#id patterns"), by design, since it exists to serve ID-fragment rename. A key rename needs a **parallel** pair — `referenceMatchesKey()`/`replaceKeyInReference()` — that: (a) matches `keyref` by whole-value equality against the old key name, (b) matches `conkeyref` by its **prefix** (`value.split('/')[0]`) rather than the suffix `replaceIdInReference` matches for ID rename, and (c) separately finds/rewrites the defining `keys="..."` token itself, which isn't part of the `REF_ATTR_NAMES` (`href`/`conref`/`conkeyref`/`keyref`) regex at all (`referenceParser.ts:28,156`) and so isn't visited by `findReferencesToId`'s scan in the first place. Mirror the *shape* of the existing pair, don't try to extend it.
- Extend `handlePrepareRename`/`handleRename` in `rename.ts`: if the cursor isn't on an `id`, fall back to checking for a key token via `findKeyAtOffset`.
- Reuse `KeySpaceService` (already resolves key definitions and can be walked for `keyref`/`conkeyref`/`keys` usages) instead of a fresh reference scan — this also gets keyscope-qualified rename correctness (a key renamed inside a nested `@keyscope` must not collide with a same-named key in a sibling scope) essentially for free, since it's the same infrastructure that made **Conkeyref-Verified Rename** correct for IDs. Worth the care: per the knowledge graph, `KeySpaceService` is the single most-connected node in the whole codebase (73 edges, largest of any hub) — it's already the widest blast-radius dependency in the project, so this feature's tests need to specifically cover keyscope-nested and multi-key-`keydef` cases, not just the flat case.
- Guard: reject rename if the new key name collides with an existing key visible in the same scope (surface as a `prepareRename` error, matching existing UX for duplicate IDs).

**Files touched:** `server/src/utils/referenceParser.ts`, `server/src/features/rename.ts`, new tests in `server/test/rename.test.ts`.

**Testing:** unit tests mirroring existing ID-rename suite; add keyscope-nested and multi-key-`keydef` cases.

**Status: shipped**, matching the design above with one scope decision made
explicit during implementation: **no preemptive prepareRename-time collision
guard was added.** Tracing the existing ID-rename code confirmed it doesn't
have one either — a resulting duplicate ID is left to surface as a normal
`DITA-ID-002`/`DITA-ID-003` diagnostic after the fact, not blocked at
rename time — and `DITA-KEY-004` already exists as key rename's equivalent
safety net (`KeySpaceService`'s `duplicateKeys` tracking). Adding a
preemptive check here would have meant giving `handlePrepareRename` a
`KeySpaceService` parameter it doesn't have today, diverging from the
established ID-rename UX rather than matching it — so this plan's original
"reject rename if it collides" line was corrected to the simpler, actually-
consistent behavior once traced against the real code.

Also confirmed and covered by tests: an indirect `keyref` chain
(`<keydef keys="alias" keyref="renamedKey"/>`) is a genuine usage of the
key being renamed, not just content-level `keyref`/`conkeyref` — the
generic `keyref="..."` attribute scan finds it on any element, keydefs
included, so chained keys stay consistent through a rename without special-
casing. 27 new tests (16 in `referenceParser.test.ts`, 11 in
`rename.test.ts`); full server suite (1,003 tests) and coverage
(93.0%/83.3%/94.3% lines/branches/functions, above the 90/80/90 thresholds)
verified green via `cd server && npm run coverage`.

**Post-ship hardening pass:** a `/code-review` run against the shipped diff
(8 parallel finder agents, independently verified rather than taken at face
value) surfaced 8 issues, all fixed:

- **`resolveKey()` following `@keyref` chains past the definition being
  renamed** — renaming an indirect/alias key (`keys="alias" keyref="target"`)
  silently left every direct usage of the alias unrenamed. Fixed by adding
  `KeySpaceService.resolveKeyEntry()` — the same scope-aware lookup as
  `resolveKey()`, but without following the chain — used wherever rename
  needs "which definition does this name refer to," not "what does it
  resolve to."
- **`stripReltables()` deleting rather than blanking** `<reltable>` content,
  undercounting `sourceLine` for any keydef after one in the same map — the
  single most likely real-world trigger of the sourceLine-mismatch class,
  since reltables are mainstream. Fixed to blank (preserve line count),
  matching `stripCommentsAndCDATA`'s existing approach.
- **`sameKeyDefinition`'s undefined-`sourceLine` fallback over-matching**
  across different keyscopes sharing a key name — closed the two concrete
  causes: the anchor search now tolerates whitespace around `=`
  (`keys = "..."`, previously silently unanchored), and each token in a
  multi-key attribute gets its own line instead of the first token's line
  reused for all of them (closes the multi-line-attribute variant too).
- **No validation that a new key name is whitespace-free** — a rename
  target containing a space would silently split one key into two in a
  multi-key list. Now refused outright.
- **No `KeySpaceService` degraded to a silently-incomplete "successful"
  rename** — unlike ID rename (only `conkeyref` needs it), key rename needs
  `KeySpaceService` to verify *every* `keyref`/`conkeyref` match. Now
  refuses the whole rename rather than renaming only the definition and
  leaving every usage dangling with no signal the editor surfaces.
- **Duplication** between the id-rename and key-rename code paths —
  consolidated into shared `collectCrossFileEdits()` (traversal) and
  `buildEditsForVerifiedRefs()` (verify-then-edit) helpers, parameterized by
  the two paths' differing match/rewrite logic.
- **`findRootMap()` had no in-flight dedup** (unlike `buildKeySpace()`'s
  `pendingBuilds`), so concurrent `resolveKey`/`resolveKeyEntry` calls for
  files in the same directory — routine for a heavily-`keyref`'d key's
  rename — fired redundant concurrent directory walks on a cold cache. Fixed
  with the same dedup shape as `buildKeySpace()`.

19 new tests added across `rename.test.ts` and `keySpaceService.test.ts`
covering each fix; full suite (1,011 tests) and coverage
(93.05%/83.35%/94.11%/93.05%) verified green again after the pass.

### 3.2 Publishing Profiles — ✅ SHIPPED

**Gap today:** `publishCommand.ts` prompts for transtype/output/ditaval on every run (or uses fixed settings). Teams that publish to multiple outputs (e.g. `html5` + `pdf` + a filtered `html5` variant) redo the same choices repeatedly.

**Design — sharpened with the exact shape already in the code** (second okf-rs pass, tracing `executePublish` → `DitaOtWrapper.publish` precisely rather than describing the flow from memory):
- New `ditacraft.publishingProfiles` setting (array of `{ name, transtype, outputDir, ditavalPath, params }`), workspace-scoped so profiles are shareable via `.vscode/settings.json`. **This isn't an arbitrary shape** — it maps almost field-for-field onto the `PublishOptions` interface `DitaOtWrapper.publish()` already takes (`src/utils/ditaOtWrapper.ts:25-31`: `inputFile`, `transtype`, `outputDir`, `additionalArgs?`) plus the new `ditavalPath?` field §4.5 adds to that same interface — so a "profile" is, almost literally, a saved `PublishOptions` minus `inputFile` (rename this plan's `params` field to `additionalArgs` to match exactly, rather than inventing a parallel name for the same thing).
- `DITA: Publish` command gains a QuickPick step when more than one profile is defined ("Use profile..." vs "Configure once"); a new `DITA: Manage Publishing Profiles` command opens a WebView (or QuickInput sequence, cheaper to build first) to add/edit/delete profiles.
- Persist "last used profile" per workspace so repeat publishes are one click.
- **A blast-radius fact worth designing around:** `DitaOtWrapper.publish()` has **three** callers, not just the publish command — `executePublish` (publish), `generateHtml5OutputIfNeeded` (live preview), and `executeValidation` (`DITA: Validate Entire Guide Using DITA-OT`). Since `PublishOptions` is genuinely shared across all three, output-directory handling needs care: `DitaOtWrapper.getOutputDirectory(): string` takes **zero parameters** today (`ditaOtWrapper.ts`) — it's a single global read, called by both `executePublish` and preview's `generateHtml5OutputIfNeeded`. A profile's `outputDir` must **not** be threaded through that shared zero-arg getter (that would silently redirect the live preview's output location too) — pass it explicitly as part of the `PublishOptions` object handed to `publish()` for the profile-driven call instead, leaving `getOutputDirectory()` and preview's behavior untouched.

**Files touched:** `src/commands/publishCommand.ts`, `src/utils/ditaOtWrapper.ts` (no interface change needed here beyond what §4.5 already adds), `src/utils/configurationManager.ts`, `package.json` (setting schema + new command), new `src/commands/publishProfilesCommand.ts`.

**Testing:** extend existing `publishCommand` test suite with profile-selection and persistence cases.

**Status: shipped**, with two scope decisions made explicit during
implementation:

- `ditavalPath` landed on `PublishOptions` as part of *this* item rather than
  waiting for §4.5 — a profile without ditaval support would be an
  incomplete deliverable, and §4.5's preview picker can now reuse the same
  field instead of redoing the interface change. `DitaOtWrapper.publish()`
  pushes it as a single `--filter=<path>` token, matching the exact form
  already documented for the generic `ditacraft.ditaOtArgs` escape hatch
  (`package.json`'s own example).
- "Persist last used profile... repeat publishes are one click" was
  implemented as *sort-to-top-and-label* in the publish picker (written to
  a new `ditacraft.lastUsedPublishingProfile` workspace setting, following
  the exact same `ConfigurationTarget.Workspace` precedent `ditacraft.rootMap`
  already uses — not `context.workspaceState`), not a picker-skipping
  auto-publish. Bypassing the picker entirely risks silently republishing
  the wrong target on a workspace with several profiles; one click to
  confirm the pre-highlighted choice is the safer interpretation of "one
  click."
- `DITA: Manage Publishing Profiles` is a QuickPick-driven add/edit/delete
  flow (the plan's "cheaper to build first" option), not a WebView. A
  `.ditaval` filter is chosen via `showOpenDialog` (not free-text) and
  stored workspace-relative, resolved back to absolute via a small
  `resolveDitavalPath()` helper — consistent with treating a path that must
  already exist as a browse target, the same reasoning §3.3 below applies
  to image insertion's `href`.
- Client-only change (`ConfigurationManager`'s typed `DitaCraftConfiguration`
  wasn't touched) — profiles are read directly via
  `vscode.workspace.getConfiguration('ditacraft')`, since that typed layer
  is a curated subset for frequently-read scalar settings, not every
  setting in `package.json`, and a nested array-of-objects doesn't fit its
  existing shape.
- Tests: command-registration plus the pure `resolveDitavalPath()` helper's
  behavior (`src/test/suite/publishProfilesCommand.test.ts`) — profile
  add/edit/delete and the `ConfigurationTarget.Workspace` writes behind
  "remember last used" aren't exercised, since this project's test-electron
  run has no workspace folder open (documented precedent:
  `securityAndEdgeCases.test.ts`'s "single-file mode" note), and a
  workspace-scoped settings write needs one.

**Post-ship hardening pass:** a second `/code-review` run (8 parallel finder
agents, alongside §3.1's rename feature) surfaced four real bugs in this
feature, all fixed:

- **`promptForDitaval`'s browse-cancel silently cleared an existing
  filter.** Backing out of the native file picker (`showOpenDialog`
  returning nothing) fell through to the same `return ''` as the explicit
  "No filter" choice — editing a profile that already had a `.ditaval`
  filter and changing your mind mid-browse wiped it with no warning. Fixed
  by looping back to the filter-choice QuickPick instead of defaulting to
  "no filter" on a cancelled browse.
- **Multi-root workspace mismatch between how a `.ditaval` path is stored
  and how it's resolved.** `promptForDitaval` stored the picked file via
  `vscode.workspace.asRelativePath`, which resolves against *whichever*
  workspace folder contains the file — but `resolveDitavalPath` always
  re-joins a relative value against `workspaceFolders[0]` only. In a
  multi-root workspace, picking a `.ditaval` file that lives under the
  second (or later) folder silently stored a relative path that resolved
  to the wrong location on publish. Fixed with a new `storeDitavalPath()`
  helper: store relative-to-`workspaceFolders[0]` only when the picked file
  is actually under that folder, otherwise fall back to an absolute path —
  keeping storage and resolution consistent by construction.
- **A profile's `outputDir` never got the `${workspaceFolder}`
  substitution** that `ditacraft.outputDirectory` gets in
  `DitaOtWrapper.loadConfiguration()`. Because a profile's `outputDir` is
  deliberately threaded through `executePublish`'s `overrides` rather than
  the shared zero-arg `getOutputDirectory()` (see the design note above —
  that's what keeps a profile from silently redirecting live preview's
  output too), it never passed through that substitution step at all. A
  profile's output directory literally typed as `${workspaceFolder}/out`
  would have published into a directory named `${workspaceFolder}`. Fixed
  with a new `resolveProfileOutputDir()` helper mirroring the same
  substitution, applied in `publishCommand.ts` before the override is used.
- **`pickTranstype`'s uncached `new DitaOtWrapper()` + installation
  verification on every "Add"/"Edit" step** was flagged for efficiency, but
  traced against the rest of the codebase and found to be the *existing*
  convention — `getDitaOtWrapper()`'s singleton (`extension.ts`) isn't used
  by any of the five command modules that construct their own
  `DitaOtWrapper()`, this one included. Fixing it in isolation here would
  make this one call site inconsistent with the other four rather than
  fixing a regression; **deferred** as a separate cross-cutting follow-up
  (switch all five call sites to `getDitaOtWrapper()` together), not
  bundled into this pass.

3 new tests added to `publishProfilesCommand.test.ts` covering
`resolveProfileOutputDir`; full client type-check, lint, and
`compile-tests` verified clean (this sandbox cannot run the
`@vscode/test-electron` suite itself — see Testing note above).

### 3.3 Image Insertion with Automatic `<fig>` Wrapper — ✅ SHIPPED

**Gap today:** authors hand-write `<image href="..."/>` or `<fig><title/><image/></fig>`, and the missing-alt-text check (`DITA-SCH-030`) only fires after the fact.

**Design:**
- New `DITA: Insert Image` command (also exposed as an editor context-menu item): `showOpenDialog` filtered to image extensions, compute a workspace-relative `href`, prompt for optional caption. If a caption is given, insert a `<fig><title>caption</title><image href="…"><alt>…</alt></image></fig>` skeleton; otherwise a bare `<image href="…"><alt>…</alt></image>` (or a self-closing `<image href="…"/>` when no alt text is given).
- **Correction to the original draft:** it proposed checking whether `<fig>` is valid at the cursor's containing element by reusing `server/src/data/ditaSchema.ts`'s content-model data. That data is **server-side only** — it's inside `server/src/`, on the LSP process, and the client (`src/commands/`) has no import path to it under the client-server split this project deliberately maintains (`CLAUDE.md`: "client extension handles UI commands... a separate LSP server handles all language intelligence"). A client command reaching across that boundary would be a first-of-its-kind architecture violation, not a small shortcut.
  - **v1 (recommended):** skip the pre-check. Always offer the `<fig>` wrapper when a caption is given; if it's actually invalid at that cursor position, the existing DTD/content-model validation phase already flags it immediately as a normal diagnostic — the author gets the same feedback loop as hand-typing invalid markup, at zero new plumbing cost.
  - **Stretch (only if v1's diagnostic-driven UX proves too indirect in practice):** add a small custom LSP request (e.g. `dita/validParentElements`) that the completion provider's own logic could answer cheaply, and have the client await it before deciding whether to offer the wrapped or bare form. Scope this as a separate follow-up, not bundled into the initial command.

**Files touched:** new `src/commands/insertImageCommand.ts`, `package.json` (command + menu entry), tests in `src/test/suite/`.

**Status: shipped**, matching the design above with two scope decisions
made explicit during implementation:

- **`href` is computed relative to the current document's own directory,
  not the workspace root** — the plan's draft said "workspace-relative,"
  but that's not how DITA resolves `href`s anywhere else in this codebase.
  Every reference-resolution site on the server (`referenceParser.ts`,
  `KeySpaceService`) resolves an `href` against the *referencing file's*
  directory, and matching that convention means an inserted `href` behaves
  identically to one an author would hand-type. Implemented as
  `computeImageHref(documentDir, imagePath)`, a pure, directly-tested
  helper (`path.relative` + forced forward slashes, so the stored value is
  a platform-independent URI reference regardless of the authoring OS).
- **A separate alt-text prompt, not just a caption-derived one.** The
  plan's example markup shows both `<title>caption</title>` and
  `alt="…"`, without specifying where `alt` comes from. Since alt text is
  what `DITA-SCH-030` actually checks for absence (a caption is not a
  substitute for it — a screen reader doesn't read `<title>`), the command
  prompts for alt separately, defaulting its input box to the caption text
  (a reasonable starting point the author can edit or clear) rather than
  always duplicating it or leaving it silently unprompted.

The command is gated (editor context, palette, and its own runtime guard)
to `.dita`/`.ditamap`/`.bookmap` — deliberately excluding `.ditaval` via
`isEligibleDocument()`, since a filter file isn't content and can't
contain image markup, even though it shares the `dita` language ID with

cannot run the `@vscode/test-electron` suite itself — see the Testing

**Post-ship hardening pass:** a `/code-review` run surfaced three real
issues, all fixed:

- **Alt text was emitted as the deprecated `@alt` attribute** instead of
  the `<alt>` child element. `DITA-SCH-011` flags `@alt` as deprecated for
  DITA 1.0-1.3 — so every image the command inserted *with* alt text (the
  accessibility-conscious path it was actively encouraging) immediately
  triggered a warning on its own generated markup. Fixed by emitting
  `<image href="…"><alt>…</alt></image>` instead — `DITA-SCH-030` accepts
  either form for "has alt text," so this satisfies the accessibility
  check without tripping the deprecation one. The alt-text prompt's own
  reminder text was also citing `DITA-SCH-011` for the *missing*-alt case,
  which is backwards (011 fires on the attribute's presence, not its
  absence) — corrected to reference `DITA-SCH-030`.
- **The editor-context and command-palette `when` clauses matched
  `.ditaval` files** via `resourceLangId == dita` (all four DITA
  extensions share that language ID), contradicting the command's own
  runtime guard and doc comment, both of which deliberately exclude
  `.ditaval`. Fixed by dropping `resourceLangId` from this command's
  `when` clauses in favor of explicit `resourceExtname` checks only —
  matching the narrower gating `restructureMapCommand` already uses for
  its own `.ditamap`/`.bookmap`-only scope, rather than inventing a new
  pattern.
- **`computeImageHref` could silently insert an OS-absolute path as an
  `href`.** `path.relative()` has no common root to compute from when the
  document and the picked image are on different Windows drive letters,
  and falls back to returning the absolute target path unchanged — which
  isn't a valid relative URI reference. `computeImageHref` now detects
  that fallback (`path.isAbsolute()` on its own result) and returns
  `undefined`, and the command shows an error instead of inserting broken
  markup. Covered by a Windows-only regression test (guarded with
  `this.skip()` on other platforms, the same conditional pattern already
  used in `keySpaceResolver.test.ts` for platform-specific path
  behavior), since POSIX always has a common root (`/`) and can't
  reproduce this case.

**Later polish pass (post-v0.9.0 scope, user-requested):** two targeted
improvements to the already-shipped command, not a new feature:

- **Copy an out-of-workspace image in, instead of only linking to it or
  hard-erroring.** The OS file picker's default location (Downloads,
  Desktop) is very often outside the workspace; previously the command
  would either insert a long, fragile `../../../Downloads/foo.png`-style

  picked image isn't under any open workspace folder
  (`vscode.workspace.getWorkspaceFolder()`), the command asks whether to

  cross-drive hard-error case for anyone who accepts the copy (the copy

- **Optional width/height or scale on the inserted `<image>`.** Both are
  real DITA `<image>` attributes — verified against the OASIS DTD

  not assumed from memory — `height`/`width`/`scale` are `NMTOKEN`-typed,

### 4.4 Move Topic with Reference Updates — ✅ SHIPPED

**Gap today:** moving/renaming a `.dita` file in the Explorer silently breaks every `href` that pointed at it — there's no safety net, unlike the ID/key rename above.

**Design:**
- Confirmed clean slate: no `onDidRenameFiles`/`onDidCreateFiles`/`onDidDeleteFiles` listener exists anywhere in `src/extension.ts` or `server/src/server.ts` today, so there's no prior behavior to reconcile with.
- Register a `vscode.workspace.onDidRenameFiles` listener (client-side, `src/extension.ts`) filtered to `.dita`/`.ditamap` URIs.
- On event, ask the LSP server for all references to the old path via a new `dita/computeMoveEdits` request, built on `workspaceScanner.collectDitaFiles` + a target-path-matching pass over `href`s (not `referenceParser.findReferencesToId`, which is ID-fragment matching — this needs whole-`href`-value matching instead).
- **A precise, verified reuse point — and a real gap to fix along the way:** `href`→file-path resolution (`path.resolve(<containing-dir>, parseReference(value).filePath)`) is currently duplicated **four separate times**, each a slightly different inline copy: `crossRefValidation.ts:116`, `definition.ts:110`, `documentLinks.ts:202`, `circularRefDetection.ts:134`. None of them is exported as a shared utility. Building Move Topic is the natural moment to extract a `resolveHrefPath(containingFilePath, hrefValue): string` helper into `referenceParser.ts` or `textUtils.ts` and have all five call sites (the four existing plus this new one) use it — consistent with the project's own established pattern of consolidating logic once a third or fourth independent copy appears (see `resyncStackToMatch()`, `isPathWithinWorkspace()` in the v0.8.2 changelog).
- **Corrected risk note on `isPathWithinWorkspace()`:** the original draft of this plan said this feature "needs the same boundary check" as the guarded href-resolution sites. On closer inspection that's imprecise — `isPathWithinWorkspace()` guards sites that resolve *one* href from an open document and then *open/read* whatever path results (hover, definition, completion, etc. — confirmed via the knowledge graph: exactly 8 importers of `isPathWithinWorkspace()`, all matching that "resolve-then-open" shape). Move Topic's matching pass instead follows the `workspaceScanner.collectDitaFiles()` + `referenceMatchesTarget()` shape already used by `rename.ts` for cross-file ID rename: it **enumerates files already bounded to `workspaceFolders`** and only compares each one's resolved hrefs against a known target — it never opens an attacker-influenced path, so it's safe by construction rather than by an added guard. When the `resolveHrefPath()` extraction above lands, keep that distinction intact: call sites that resolve-then-open still call `isPathWithinWorkspace()` after resolving; the enumerate-then-compare sites (rename, and this new move-refactor) don't need to, and adding a redundant check there would just be noise, not defense-in-depth.

### 5.2 Batch metadata update — ✅ SHIPPED

**Design:** multi-select in DITA Explorer → bulk-set `<prolog>`/profiling attributes, validated against `SubjectSchemeService` controlled values so a batch edit can't introduce a `DITA-PROF-001` violation across many files at once.

Each file's target value is checked against a per-file `SubjectSchemeService` snapshot before building the edit — a value not in that attribute's controlled list skips the file with a reason (`"bogus-value" not allowed for @audience on <topic> (allowed: external, internal)`) instead of writing an invalid value, so a batch operation can never introduce a fresh `DITA-PROF-001` across many files at once. Files are read under `mapWithConcurrency`/`MAX_CONCURRENT_READS`, the same bounded-concurrency helper §5.1 established.
- **New client command `ditacraft.batchUpdateMetadata`** (`src/commands/batchMetadataCommand.ts`): resolves the effective file selection (preferring the full multi-selection, filtered to nodes with a `filePath` that `exists` — skips `keydef` entries and already-missing files) → prompts for the attribute (QuickPick of the known profiling attributes plus a custom "Other…" entry) → prompts for the value (empty removes) → sends the request → reuses `findReplaceCommand.ts`'s `buildConfirmableWorkspaceEdit()` directly (both features produce the same LSP `WorkspaceEdit` shape, so no new conversion code needed) → `vscode.workspace.applyEdit()`, which shows the same native multi-file "Refactor Preview" UI §5.1 established. Skipped files are reported by name (up to 3, then "and N more") in a warning message alongside a successful apply, or as the sole message when nothing was updated at all.

**Files touched:** new `server/src/features/batchMetadata.ts`, `server/src/server.ts` (request registration), new `server/test/batchMetadata.test.ts` (17 tests, 3 more added in the code-review pass below — set/replace/remove, subject-scheme accept/reject, missing-root-element and unreadable-file skips, in-memory-buffer preference, mixed-outcome batches, XML-escaping), new `src/commands/batchMetadataCommand.ts`, `src/commands/index.ts`/`src/extension.ts` (export, `canSelectMany: true`, command registration), `package.json` (top-level command entry + `view/item/context` multi-select menu entry, gated the same way as the existing `ditacraft.showMapVisualizer` entry), new `src/test/suite/batchMetadataCommand.test.ts` (pure selection-reduction/label/summary tests; the request/response round-trip itself is covered server-side).

**Post-ship `/code-review` pass (single-pass, 4 findings — all confirmed and fixed):**
- **Correctness: root-element detection could match a tag-like fragment inside a leading comment.** `ROOT_TAG_PATTERN` scanned the raw document text, so a file like `<!-- TODO: remove <placeholder foo="x"/> before publishing --><topic id="t1">...` matched `<placeholder>` inside the comment as the "root element" — the batch write then landed on that comment fragment while `<topic>`, the real root, was silently untouched, yet the file was still reported as updated. Fixed by matching against `stripCommentsAndCDATA(content)` first (the same helper `findReplace.ts`/`profilingValidation.ts` already use), which blanks comment/CDATA spans while preserving line/character structure so the match's offsets still apply correctly to the original text.
- **Correctness: subject-scheme validation relied on the shared service's already-registered state instead of each file's own scheme.** The handler validated against the shared `SubjectSchemeService` instance directly, whose `registeredSchemes` is only populated as a side effect of `ValidationPipeline`'s own per-document Phase 7 — a file multi-selected straight from the DITA Explorer tree without ever being opened/validated first would see no scheme data at all, so validation silently no-opped and an out-of-scheme value could be written across every selected file. This is exactly the shared-mutable-state hazard `validationPipeline.ts`'s own Phase 7 comment warns about. Fixed by resolving each file's own subject-scheme paths via `keySpaceService.getSubjectSchemePaths(filePath)` and validating against `subjectSchemeService.snapshotFor(schemePaths)` — a pure, per-file lookup immune to concurrent files in the same batch belonging to different maps — newly threaded through `server.ts`'s request registration as an optional parameter (falls back to the shared service's current state when no `keySpaceService` is available, matching the prior behavior).
- **Efficiency: unbounded-in-spirit sequential file reads.** Contrary to this section's original design note, reading files one at a time in a `for..of` loop has no actual advantage over the bounded-concurrency approach §5.1 already established for the identical job, and needlessly serializes what could run in parallel for a larger multi-selection. Fixed by reusing `workspaceValidation.ts`'s `mapWithConcurrency`/`MAX_CONCURRENT_READS`, restructuring the per-file logic into an isolated `processFile()` so it can run under bounded concurrency while still returning results in original-file order.
- **Correctness: the metadata value input wasn't trimmed.** `promptForAttribute`'s custom-attribute input already trimmed its own free-text entry, but the sibling value prompt did not — a value typed with a trailing space (easy via copy/paste) was sent and written verbatim into the XML attribute across every selected file. Fixed by trimming the raw input box value (only leading/trailing whitespace; the space-separated-tokens convention for multiple values is unaffected).

Verified: full client `check-types`/`compile-tests`/`lint` clean; full server suite (1090 tests, up from 1087) passing with coverage 93.28%/83.91%/94.32%/93.28% (all above the 90/80/90/80 thresholds), `batchMetadata.ts` itself at 98.03%/93.33%/100%/98.03%; the comment/root-detection and per-file scheme-scoping fixes each cross-checked with a dedicated regression test.

### 5.3 Visual DITAVAL condition editor — ✅ SHIPPED

**Design:** WebView (same panel pattern as `mapVisualizerPanel.ts`) listing every profiling attribute/value pair discovered via `SubjectSchemeService`, with include/exclude/flag toggles that serialize back to `.ditaval` XML. Builds directly on 4.5's condition-matching logic. **Verified precedent for the webview's own message protocol:** `mapVisualizerPanel.ts` already runs a simple bidirectional dispatch — the webview's HTML posts `{ command: 'openFile', filePath }` / `{ command: 'refresh' }` via `vscode.postMessage`, the panel receives them through `webview.onDidReceiveMessage` (`mapVisualizerPanel.ts:43`). A condition editor's toggle messages are a direct extension of that same shape.

**Status: shipped, matching the design above, with one addition and one deliberate simplification found before implementation:**

- **New server request `dita/getSubjectSchemeAttributes`** (`server/src/features/ditavalConditions.ts`): given a context file (the `.ditaval` being edited), resolves that file's subject scheme(s) the same per-file way `batchMetadata.ts` (§5.2) does — `keySpaceService.getSubjectSchemePaths(filePath)` then a pure `SubjectSchemeService` lookup — and enumerates every controlled attribute with its merged, deduplicated value list (element-scoped buckets merged into one, since a DITAVAL `<prop>` rule is attribute/value driven only and never targets a specific element) plus each value's hierarchy path when the scheme defines one. Needed a small **addition** to `SubjectSchemeService`: a new public `getSchemeData(schemePaths)` method exposing the raw `validValuesMap`/`hierarchyPaths` structure for an explicit scheme path list (the existing `snapshotFor()` returns only the narrower `SubjectSchemeQueries` lookup-by-name surface, not something an enumeration UI can iterate over).
- **New client command `ditacraft.editDitavalConditions`** (`src/commands/ditavalConditionEditorCommand.ts`): resolves the target `.ditaval` file from a DITA Explorer tree item / `vscode.Uri` (context menu) / active editor — the same resolution order `ditacraft.showMapVisualizer` established — and opens `DitavalConditionEditorPanel`.
- **New WebView panel `DitavalConditionEditorPanel`** (`src/providers/ditavalConditionEditorPanel.ts`): parses the open `.ditaval` file's existing `<prop>` rules (`ditavalParser.ts`'s `parseDitavalRules`, already shipped for §4.5), merges them with the server-discovered scheme attributes (`mergeAttributeState`, pure — see below), and renders each attribute as a group of value chips. Each chip's next click-state is precomputed host-side (`nextConditionAction`) and embedded directly in its click handler, so the webview's own script never needs to know the unset→exclude→include→flag→unset cycle order — one source of truth, kept in the pure helper module, not duplicated into the HTML template's inline JS. A value already in the file but not offered by the scheme (a hand-typed/legacy value) still gets its own row rather than being silently dropped. Toggling a chip (or adding a new attribute/value via the bottom form) regenerates the whole document via `buildDitavalDocument()` and applies it with `vscode.workspace.applyEdit()` directly — no confirmation-preview step, unlike §5.1/§5.2's multi-file operations, since this is a single, currently-open document the webview itself already *is* the live preview for (the same UX class as typing in an editor, not a batch refactor).
- **New pure helper module `src/utils/ditavalConditionState.ts`** (`mergeAttributeState`, `applyConditionToggle`, `nextConditionAction`) and a new `buildDitavalDocument()` serializer added to the existing `ditavalParser.ts` — split out from the panel class specifically so the merge/toggle/serialize logic is unit-testable without any VS Code API surface, matching this project's established pattern of extracting pure helpers out of otherwise VS Code-bound providers/commands (e.g. §5.2's `resolveSelectedFileItems`/`describeBatchLabel`).
- **Deliberate v1 simplification, surfaced directly in the webview as a standing warning banner (not just a doc comment):** saving from this editor regenerates the file's `<prop>` rules from the toggle state. Value-specific rules the editor doesn't have a scheme-derived chip for are still preserved (they get their own row via `mergeAttributeState`, never silently dropped), and value-less "default for this attribute" rules already in the file are carried through unchanged as `otherRules`. But anything the parser doesn't recognize at all — comments, `<style-conflict>` blocks, any element other than `<prop>` — is **not** preserved. A full incremental-edit model (patching only the specific `<prop>` elements that changed, leaving everything else in the file untouched) is real future work, not folded into this v1 pass.

## 8. Cross-Cutting Requirements (apply to every item above)

- **Tests first, matching existing suites** — server-side logic gets Mocha tests under `server/test/`, client commands get suite tests under `src/test/suite/`, following the `createDoc()`/`waitForErrors()` helper patterns already documented in `CLAUDE.md`.
- **i18n** — any new diagnostic or user-facing message needs matching keys in both `server/src/messages/en.json` and `fr.json`.
- **Workspace-boundary safety** — any new code that resolves-then-opens an `href`/file path must call the shared `isPathWithinWorkspace()` guard (per the v0.8.2 hardening pass); this is the most common regression risk category recorded in `ROADMAP.md`'s recent-changes history. (Code that only *enumerates* already-workspace-bounded files and compares against a known target — the `rename.ts`/§4.4 pattern — doesn't need a second guard on top; see §4.4's corrected risk note for why conflating the two isn't just imprecise but actively unhelpful for reviewers checking "was this guarded?".) And per §2.1: verify there's exactly one implementation of this guard per process (server, client) before assuming a same-named symbol is it.
- **Never create a `.ditacraft/` folder in the user's workspace** — confirmed as an explicit, deliberate project policy, not merely an absence of precedent: `src/utils/logger.ts:58` states it directly ("Always use temp directory for logs (never create .ditacraft folder in workspace)"). Every new persistent-state proposal in this plan already complies (§4.1's `ditacraft.templatesPath` points at a user-chosen directory; §3.2's publishing profiles live in `.vscode/settings.json`) — but this is exactly the kind of convention a new contributor implementing §4.1/§4.2/§4.4 wouldn't discover without either reading `logger.ts` or hitting this document, so it's called out explicitly rather than left implicit.
- **MCP surface stays read-only — on purpose, not by oversight.** Verified: all 6 existing MCP tools (`dita_validate`, `dita_context_snapshot`, `dita_key_space`, `dita_map_structure`, `dita_resolve_reference`, `dita_explain_key`) are queries; none applies a `WorkspaceEdit` or otherwise mutates a file. None of this plan's refactoring commands (§3.1 rename key, §4.4 move topic, §5's extract topic) should get an MCP tool in v0.9.0 — an AI agent invoking a workspace-mutating tool needs different confirmation/undo semantics than these six queries do, and designing that is a separate piece of work, not a checkbox to tack onto a feature that already has a VS Code-native UI. Naming it here so it reads as a scoped-out decision for v0.9.0 rather than a gap nobody noticed — candidate for Milestone 8+ if there's real demand for agent-triggered refactors.
- **`ROADMAP.md` bookkeeping** — check off items as they land and fold each into the "Recent Changes" section with test-count deltas, matching the existing changelog format.
